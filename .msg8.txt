feat: separate the two pipelines, richer palettes, in-app install, smoother tap

Four things the user asked for, plus a CI trap they asked about.

1. Separate the server pipeline from the app pipeline.

They asked whether the two were separate; they were not - build.yml still carried a
build-android-apk job, so every upstream commit rebuilt the app too, for an app whose
code rarely changes. Removed. Server keeps its current behaviour (upstream commit or
manual). The app now has exactly one entry point: apk-only.yml, manual, publish opt-in.

Consequence, documented rather than left to be discovered: server releases no longer
carry an APK, so releases/latest/download/pumpkin-shell.apk is no longer dependable -
latest is usually a server release. README and ANDROID.md now point at the Releases
page and at the in-app updater instead of claiming a permanent link.

Also folded in the stamp decoupling: the server tag no longer needs to agree with any
APK versionCode, because those releases contain no APK.

2. Six more palettes, three of them light.

"Still dark mode" - all six existing schemes were dark greys differing mostly in accent,
so switching barely changed the overall look. Added 3 light (晨雾白 / 暖米色 / 淡紫晨光)
and 3 genuinely tinted dark (深紫暮色 / 墨绿深林 / 酒红微醺).

The delegated draft of these failed contrast: it asserted all thirteen pairs passed,
but 晨雾白's ok colour measured 4.19, 暖米色's button text 4.09 and ok 4.06, and
淡紫晨光's ok 3.77 - all under 4.5. Recomputed the WCAG ratios myself and darkened
those four values until they cleared with margin.

isLight is now a property of the palette rather than a separate dark flag, because the
two can disagree: a light palette with dark widgets is incoherent. It drives the miuix
scheme, the glass highlight strength, and the system bar icon colour - without the last
one, white status icons sit on a pale gradient and vanish.

3. App updates download and install in-app.

Previously openUrl(): out to a browser, and the user had to find the file and tap it.
Now the download runs in the app with progress in the About card, then goes to the
system installer via FileProvider (file:// URIs throw FileUriExposedException since
targetSdk 24). The provider exposes exactly one directory, not private storage generally.

Source order is now the user's chosen source, then official direct, then the general
mirror, then built-ins - and there is a picker for it. This was not cosmetic: the old
order reused the server's "last good mirror" first, and the observed in-app download
sat at 3.3MB of 13.7MB against a slow mirror. It also no longer writes good_prefix,
which would have let an app download overwrite the server's remembered mirror.

Review findings applied: .part files are deleted on failure or cancel instead of being
left behind; progress is -1 (bar hidden) when Content-Length is absent, rather than a
bar pinned at 0% that reads as a hang; the duplicate toast that overwrote itself is
gone; and a downloaded package is remembered so returning from the "install unknown
apps" screen installs it directly instead of re-downloading 14MB.

4. Tapping a bottom-bar tab no longer stutters.

Dragging was smooth, tapping was not. The file has no clickable - touch taps are served
by the drag gesture path - so onDragStarted already animates the value toward the
pressed tab, and onDragStopped then called updateValue(targetIndex) unconditionally,
cancelling an animation at full speed and restarting the same spring from zero velocity.
The official implementation does not call updateValue there. Now it only does so when a
drag actually left the value between two tabs, which is the case that genuinely needs
re-centering.
